Implementation plan

Hear Her Story

A screen-reader accessibility mod for Sam Barlow's Her Story — turning a game about searching a police video archive into one that can be played entirely by ear.

Target Unity 5.0.1f1 · Mono · x86 Loader MelonLoader 0.7.3 Speech UnityAccessibilityLib

What the game is, mechanically

The player types search terms into a mock 1994 police database. The search matches transcripts of 271 short video clips — interview footage of one woman — and returns the first five matches as thumbnails. You watch clips, learn names and details, and use those to search again. There is no win condition; you stop when you understand what happened.

Almost everything that matters is already verbal: the clips are a woman talking, and the search is text. The visual layer is a skeuomorphic desktop wrapped around it. That makes this game unusually well-suited to a screen-reader mod — the gap is narrower than it first appears.

  • Search results are thumbnail images with no accessible label, so you cannot tell what you found or pick a clip.
  • Result counts, the query cap, and system messages are drawn as on-screen text that is never spoken.
  • Nothing is ever announced — not focus changes, not state changes, not the outcome of a search.

Note what is not on that list: keyboard navigation. An earlier draft of this plan claimed the game was mouse-only with no focus model to hook into. That was wrong, and the correction reshaped the project — see below.

Findings from decompilation

I decompiled the game's assemblies with ilspycmd and scanned the asset bundles directly. Three findings shape the whole design.

Decisive

The game already ships complete timed captions

The clip database is a TextAsset CSV inside sharedassets1.assets — 271 rows × 15 columns, parsed in NewUIDatabase.Awake(). Column 5 holds a plain transcript; column 9 holds timed subtitles as a %-delimited alternating text/seconds array. ClipDetail.Update() already walks it during playback.

This eliminates what would otherwise be the largest task in the project: no transcription, no alignment, no external caption files. Every spoken word already exists as timed text that the mod can read and speak. It also means search-result previews can quote the real transcript.

Confirmed

UnityAccessibilityLib fits this game exactly

The library ships a net35 build — the oldest of its three targets, and the one that matches this game's .NET 3.5-era Mono runtime. That is the compatibility question that decides the whole project, and it lands in our favour.

It also resolves the architecture question. Its speech backend, UniversalSpeech.dll, must be 32-bit; HerStory.exe and its AVPro video plugin are both 32-bit x86. No bitness mismatch.

What it gives us beyond raw speech: duplicate suppression, a repeat buffer, braille output alongside speech, rich-text stripping with custom replacement hooks, and a text-type system with a CustomBase for our own categories. It carries its own SAPI fallback when no screen reader is running. It is framework-agnostic — we supply an IAccessibilityLogger and it plugs into whichever loader we choose.

Corrected

A focus model already exists — we were looking in the wrong assembly

I first concluded the game had no keyboard or controller handling, because Assembly-UnityScript.dll contains only four input calls: mouse down/up for dragging icons, GetKey for Enter in the search box, and GetKeyUp for Escape. That conclusion was wrong. Typing into the search box plainly works, so something was handling the keyboard — and it wasn't the game's own code.

It is UnityEngine.UI.dll. InputField.OnUpdateSelected drains Unity's event queue with Event.PopEvent and feeds each key to KeyPressed. That method is an EventSystem callback, fired only for the currently-selected object — so a live EventSystem with a working input module is already running. Typing is the proof.

The shipped UI assembly also contains a complete, functional StandaloneInputModule: it reads the Horizontal/Vertical axes and Submit/Cancel buttons and dispatches moveHandler, submitHandler, and cancelHandler events. Selectable carries the matching navigation system — FindSelectableOnRight/Down/Left/Up, an automatic mode that finds neighbours geometrically, and a static allSelectables registry. Unity binds those axes to arrow keys and gamepad sticks by default.

In other words: the focus model we planned to build from scratch is largely already present. What is missing is that nothing is ever spoken.

Open

Three questions that static analysis cannot settle

What remains unknown is how much of that machinery this particular game actually uses. Serialized scenes store components by numeric class ID, and the type tables list every type a build references, not what it instantiates — so reading the asset files cannot answer:

  • Are the Selectables navigable, or is navigation.mode set to None?
  • Is firstSelectedGameObject set, so focus starts somewhere sensible on each screen?
  • Do the runtime-instantiated result thumbnails — created in PopulateDatabaseList() — participate in navigation at all? These were almost certainly only ever wired for mouse clicks.

These decide the size of Phase 02, so Phase 01 answers them at runtime rather than guessing. The likely finding is that automatic navigation is on (it is Unity's default) and the gap is confined to the dynamic thumbnails.

Orientation

The game logic is in UnityScript, not C#

Assembly-CSharp.dll is a decoy — it contains only AVPro video-plugin demos and Unity UI samples. The real game lives in Assembly-UnityScript.dll, where classes are compiled UnityScript with public virtual methods. Harmony patches them normally, with one caveat: RunQuery() is a compiled coroutine state machine ($RunQuery$139), so it must be patched at its entry and exit points rather than internally.

Why not an accessibility tree

The natural instinct for focus management is a library like AccessKit — describe the UI as a tree of nodes with roles and properties, and publish it to the platform's native accessibility API so a screen reader can explore it like a native app. That is the right architecture when building a UI toolkit from scratch. It is the wrong one here.

It is Rust-first with C bindings, so targeting .NET 3.5 Mono means hand-rolling a P/Invoke layer over a large API. Its value is publishing a tree you own — but our tree already exists as Unity Selectables that the game itself drives, so we would be mirroring state and keeping two models in sync. And a screen reader cannot run its usual virtual cursor over a game window regardless, so most of what that costs would go unused.

The simpler model wins: let Unity own focus, and speak on transition. That is what UnityAccessibilityLib is shaped for, and what game accessibility mods generally do.

Choosing the loader

Superseded

The mod ships on MelonLoader, not BepInEx

The original reasoning below chose BepInEx 5 on packaging grounds, treating the two loaders as technically interchangeable. BepInEx was tried first and crashed the game, so the mod runs on MelonLoader 0.7.3 instead; everything from Phase 01 onward was built and verified against it. Where this section and the code disagree, the code is right.

The crash was not diagnosed to root cause — the loader was swapped rather than debugged, which was the right call under time pressure but leaves an unanswered question. The remnants of that attempt are still in dist/ (a full BepInEx/ tree and a Doorstop winhttp.dll) should anyone want to revisit it.

Neither loader worked out of the box. BepInEx crashed the game outright; MelonLoader started the game fine but silently failed to load the mod, which is the harder failure to diagnose of the two. MelonLoader was chosen because that second failure could at least be traced.

The root cause is configuration, and it is two bugs stacked. MelonLoader's preferences system depends on Tomlet, whose net35 build fails at type-initialization on Unity 5.0.1's Mono — it cannot resolve a method carrying an unmanaged generic constraint through reflection. That failure is then swallowed, because MelonBase.Register() calls RegisterCallbacks() — which subscribes to the preferences events — outside the error handling that guards the initialization call three lines below it. The mod's assembly loaded, its constructors ran, and OnInitializeMelon was simply never invoked, with nothing logged anywhere: no error in Latest.log, the console, or the Unity player log.

Both problems are fixed in locally patched builds of MelonLoader and Tomlet, and both fixes are written up as upstream reports in upstream-reports/. The Tomlet fix is fully verified — all targets build, 164/164 tests pass, confirmed working on the affected runtime.

The plan's claim that reversing the loader choice would cost about a day proved roughly right in code terms — the entry point and IAccessibilityLogger are the only loader-specific pieces — but it did not price in debugging a silent failure in the loader itself.

The original reasoning, retained because it still describes the packaging trade-off correctly:

BepInEx 5 and MelonLoader are technically interchangeable here. Both support Mono games of this vintage, both bundle Harmony, both have a documented adapter for the accessibility library, and the mod code is identical under either. With no technical difference to decide on, packaging decides it: BepInEx 5 (x86 Mono, matching the 32-bit game).

BepInEx installs by extraction, so the entire mod ships as one archive with the final layout already in it. The player extracts once into the game folder and is done. There is no separate loader installer to run first, no "install X, then install this" sequence, and no version coupling between loader and mod to keep in step across releases.

That is worth more than it sounds for this particular audience. A single extract-and-play step is the most reliable install to describe in a readme and to follow with a screen reader, and it makes the whole distribution testable by unzipping into a clean copy of the game.

That packaging argument survives the switch intact, though by a different route than it was originally made. Patching the loader means shipping the loader, which means its installer is never run — so the mod bundles the whole layout and the player still extracts once. See Scope below.

What the switch does add is a maintenance obligation: shipping modified MelonLoader and Tomlet binaries means re-patching against future releases until the upstream fixes land, and carrying the attribution that Apache 2.0 and MIT require. That is a real cost, but it is a cost of patching, not of packaging.

Architecture

A single MelonLoader mod, patching the game with Harmony and speaking through UnityAccessibilityLib. No game files are modified — the mod is a drop-in, and deleting it restores the stock game. This matters for a game distributed on Steam and GOG, where patched assemblies would trip file-integrity checks.

ComponentResponsibility
SpeechThin layer over the library's SpeechManager — it already handles duplicate suppression, repeat, and braille. We add only an interrupt-versus-append policy, so a keypress cuts off the previous utterance but captions never truncate each other.
FocusWatcherObserves EventSystem.current.currentSelectedGameObject and speaks on change. Owns no cursor — Unity keeps driving selection. Where the game's own navigation has gaps, this repairs them by setting navigation.mode and neighbour links on the offending Selectables.
LabellerTurns a focused GameObject into a spoken label: role, name, state, and position in its group. This is the real work of Phase 02 — the game's elements carry no accessible names, only sprites and layout.
ClipLibraryReads dataUID once at startup; exposes transcript, duration, watched-state, and timed captions per clip.
NarratorComposes what gets spoken — result summaries, clip descriptions, captions — in one place, so phrasing stays consistent and tunable.
PatchesHarmony hooks that feed the above from game events.

Build sequence

Five phases, each genuinely dependent on the one before it, and each independently testable in-game.

01

Speech, and a survey of what's there

Goal: the game speaks — and we learn exactly how much navigation already works.

Install the loader, reference UnityAccessibilityLib's net35 build, drop the 32-bit UniversalSpeech.dll in the game root, and implement IAccessibilityLogger against the loader's logger. Prove the pipeline by announcing the main menu on load.

The same build carries a diagnostic that answers the open questions above. On each screen it dumps: the active input module's type, firstSelectedGameObject and currentSelectedGameObject, and for every entry in Selectable.allSelectables its name, IsInteractable(), and navigation.mode. A key that walks selection manually confirms whether moveHandler events actually route.

The controller is worth querying here as a second input surface — not as a feature to build, but as evidence. Unity binds Horizontal/Vertical and Submit/Cancel to gamepad inputs by default, so a connected pad already feeds the same event path. Logging live axis values and button states alongside the keyboard costs nothing extra and tests the module more sharply: arrow keys and sticks share the axes, but gamepad Submit is a separate binding from Enter, so seeing both confirms the module is processing the full input set rather than something else intercepting keystrokes.

Pairing these is deliberate: the survey needs a running game, and speech needs validating in one anyway. One session settles both — whether the loader works on a 2015 Unity build, whether the native speech library loads, and how much of Phase 02 is repair rather than construction.

02

Focus and labels

Goal: moving around any screen tells you where you are.

Scope here is set by what Phase 01 finds, and splits in two.

Labelling is required regardless, and is the bulk of the work. Every focusable element needs a spoken identity — role, name, current state, and position within its group ("result 2 of 5"). The game's UI carries none of this: elements are sprites with layout positions, and the result thumbnails are literally just images. Labels come from the game's own data via ClipLibrary wherever possible, rather than hardcoded strings.

Repair is conditional. If automatic navigation is live, this is small: set firstSelectedGameObject per screen so focus starts somewhere sane, and fix gaps where geometric neighbour-finding produces a poor order. The runtime-instantiated result thumbnails are the likeliest gap — they are created fresh on every query, so whatever PopulateDatabaseList() builds must be made navigable as it is built. If navigation turns out to be disabled outright, this grows into enabling and wiring it explicitly across each screen.

Either way the mod does not own a cursor. Unity keeps driving selection; we observe, repair, and speak. That avoids the failure mode where a parallel cursor and the game's own selection disagree.

Built and verified

What Phase 02 actually found

The open question is settled: result thumbnails are not Selectables at all. PopulateDatabaseList() instantiates each tile from imageBoxPrefab and attaches only a ClickyBox — no Button, no Selectable, no onClick. Keyboard navigation could not reach a search result by any route. Repair was therefore construction, not adjustment, though only for this one control.

Elsewhere the optimistic reading held. A live StandaloneInputModule runs with sendNavigationEvents on and every shipped Selectable set to navigation.Automatic. Nothing needed enabling; firstSelectedGameObject is simply never set, so focus started nowhere until the mod seeded it.

The build adds a bare Selectable per tile with explicit left/right links — geometric neighbour-finding is unreliable across the clipped scroll viewport — and activates through ClickyBox.JustBeenClicked(), since there is no onClick to invoke. Confirmed in play: result 1 of 4, new, 11 seconds followed by the clip's opening line.

Two defects surfaced in that same session and were fixed. Tab order was sorted purely by screen geometry, which placed the results panel after the toolbar and so skipped past the results the announcement had just pointed the player at; it is now banded — search box, results, everything else. And closing a clip left selection on an internal video object, which a patch on ShutDetailText now returns to the result the player opened.

A later session exercised the five-result cap — 137 entries matched, capped at five, all five reachable and separately labelled — and surfaced two further defects, both since fixed. SaveLoad.Load() reopens the last-viewed clip to restore a session, which the mod announced as though the player had opened it, so a returning player heard a clip summary before reaching the title screen; the restore is now bracketed and stays silent. And the all-caps softening turned the cap message into Title Case while leaving short words shouting — "Access Limited TO First 5 Entries" — because it worked word by word; it now treats a run of shouted words as one sentence, and leaves isolated acronyms alone.

Two verbosity questions are deliberately left open, because they are judgment calls that only sustained play can settle, and the log is a poor instrument for them — repetition reads worse written down than it sounds:

  • Moving off a result and back re-announces it in full. Correct behaviour on arrival; possibly wearing on a round trip.
  • The "3 of 7" group counts shift as panels open and close, because they are counted per parent. Accurate each time, but the same control can be "1 of 7" and then "3 of 7" within seconds.
03

Search and results

Goal: the core loop — type, hear what came back, choose a clip — works by ear.

The search box is the most-used control in the game, and free text entry is the whole mechanic: you hear a name in a clip, then type it. So it needs real screen-reader text-entry behaviour — echo characters as typed and words on space, announce the field and its contents on focus, read back the current text on demand, and speak deletions by naming the character removed rather than falling silent.

InputField.KeyPressed is the chokepoint every keystroke passes through, including backspace and caret movement, which makes it the right hook. The game's own InputValidate.checkChar sees insertions only, so it is not sufficient alone.

Two parts of this phase already shipped in Phase 02, because they fell out of patching PopulateDatabaseList() for navigation. The query outcome is announced — the game's own summaryText carries the entry count and the access cap, so the mod speaks that rather than recomputing it, which keeps the cap phrased as the game's rule. And each result already has a spoken identity from ClipLibrary: position, watched state, duration, and an opening line of real transcript. The cap wording remains unverified in play, per the Phase 02 note above.

What is left is the search box itself, and the normalisation announcement below.

One game-specific subtlety: the search normalises input before matching — CheckAmerican() rewrites US spellings to UK, and quoted queries switch to exact-match. On a zero-result search a blind player cannot tell a typo from a genuinely absent word, so the mod announces the normalised query — what the game actually searched for — turning a dead end into information.

Built

What Phase 03 actually found

InputField.KeyPressed was the right hook, but it is protected in the Unity 5.0.1 UI assembly, and its EditState return type is a non-public nested enum this mod cannot name. The patch therefore resolves the target through AccessTools rather than by attribute, and ignores __result entirely — it reads the field's state afterwards instead, which is the thing we actually care about. caretPosition is protected on this version too (the public property came later), so the caret is read from the m_CaretPosition backing field through a cached FieldInfo; if that ever fails to resolve, the cost is caret reporting alone and the rest of the echo survives.

The echo never interprets the keystroke. It snapshots the field's text and caret, and diffs successive snapshots by matching the unchanged text at each end — which is what lets a single hook cover insertion, backspace, forward-delete, paste and caret movement without a branch per key. Multi-character changes are read as text rather than spelled out, since those are pastes; single characters are echoed, buffered into a word, and the whole word spoken again at the space that ends it.

That snapshot has to be re-baselined wherever the game writes the field behind our back, and it does so in two places worth naming. RunQuery strips newlines from the field on every submit, and SaveLoad.Load refills it with the saved query on a restore. Left alone, either would leave a stale baseline and make the player's next real keypress announce as a bulk deletion — so both paths call SearchBox.Sync, the restore doing it from the existing finalizer that already unsets the silence flag.

The normalisation announcement needed a correction to the plan's premise. The normalised query is not readable off the database: NewUIDatabase.searchString is a field, but RunQuery is a UnityScript coroutine and keeps the normalised value in a local of its generated state machine, never writing it back. The mod recomputes it by calling the game's own public CheckAmerican, which is also the more truthful route — if the spelling tables change, the announcement follows them. Case-only differences are deliberately not reported, since CheckAmerican lower-cases everything and would otherwise fire on virtually every search; only a genuine spelling substitution, or the quoted exact-match switch, is worth a player's attention.

Not yet verified in play. The build is clean and the patch is checked at startup, but the echo's feel — particularly whether per-character speech outpaces fast typing, and whether the word-on-space repeat is confirmation or clutter — is exactly the kind of judgment the log cannot settle. It needs a session.

04

Playback

Goal: clips are watchable, and captions are available for anyone who needs them.

The clips are speech, so audio mostly carries itself. The mod announces playback start and end, and supports interrupting a clip. Because ClipDetail already tracks caption position against playback time, an optional spoken-caption mode is nearly free — valuable for deafblind players on a braille display, and for anyone who misses a line.

A "read full transcript" key exposes the whole clip as text on demand, independent of playback — the single most useful affordance for a game built on re-reading testimony for detail. This shipped early, in Phase 02, as Ctrl+T.

Built

What Phase 04 actually found

The caption mechanism is better than this plan assumed, and the difference changed the design. ClipDetail.Update() does not merely track caption position — it owns a cursor, subtitlePosition, which it advances by two through a subtitleArray of alternating text and end-time pairs, comparing each end time against PositionSeconds from the movie instance. So the mod runs no clock of its own: it watches that cursor and speaks when it moves. This is what makes scrubbing work for free — dragging the video slider resets the cursor to zero, and a parallel timer would have drifted out of step with the picture at exactly the moment the player was hunting for a line.

Everything needed here is public, which is a change from Phase 03. NowPlayTheVideo, AbortTheVideo, PlayerCancels and the fields behind them are all reachable by ordinary attribute patching. PlayTheVideo is a one-line delegate to NowPlayTheVideo, so the latter is the hook — it is the point every route into playback passes through.

Ending a clip needed one piece of care. Both exits — the clip finishing and the player stopping it — funnel into AbortTheVideo, which cannot tell them apart, so the mod brackets PlayerCancels to mark the cancel path. The distinction is worth the trouble twice over: it is a different thing to hear, and the game scores the two differently, awarding half credit for a cancel. That scoring is also why the stop key routes through PlayerCancels rather than reaching past it to the abort — a keyboard player stopping a clip should score exactly what a mouse player does.

Spoken captions are off by default, which is a deliberate reversal of the plan's framing. The clips are speech; captions spoken over them are two voices at once, and unusable as a default. They stay valuable for the cases the plan named — a braille display, or a player who wants the text — but those are choices only the player can make. The "I missed that line" case is served separately by Ctrl+K, which re-reads the caption on screen whether or not continuous captions are switched on, and is most useful precisely to the player who does not want them.

One data detail worth recording: FillDetails appends a "% %9999" sentinel before splitting, giving the game's walk a final entry no playback position can pass. Read back naively that speaks as "9999", so the caption reader skips it.

Not yet verified in play, in the same state Phase 03 is in. The specific risk here is the interaction the log cannot show: captions and the search-box echo share one speech channel, and how they behave together — along with whether per-character echo keeps up with fast typing — is what the next session needs to settle. The caption path speaks through a single call site, so rate-limiting can be added in one place if it turns out to need it.

05

Orientation

Goal: the player can hold the investigation in their head.

Sighted players keep bearings through persistent on-screen state: search history in the sidebar, tagged clips, thumbnails on the desktop. Without that, a blind player has to carry it all in memory — so this phase makes that state queryable rather than remembered.

Review keys report the current query and result count, walk the search history, list tagged clips, and give progress against the 271 total. This is what turns a technically operable game into a playable one, and it is the phase most likely to need revision after real testing.

Corrected

The caption toggle is Ctrl+J, not Ctrl+C

Unity's InputField.KeyPressed consumes Ctrl+A, C, V and X for clipboard work — confirmed in the IL, which switches on character codes 97–99 and 118–120. The search box holds focus for most of the game, so the Ctrl+C this plan originally specified would have toggled captions every time the player copied their query, and copied at the same time. The mnemonic is worse; the collision is disqualifying.

Esc survived the same check. The field does handle it — setting wasCanceled and ending editing — but a clip can only play while the detail panel is up, not the search box, so the two uses cannot both be live. The mod also leaves the key alone unless something is actually playing.

Observed

Space activates buttons, and it is the reliable key

Unity binds its Submit button to both Enter and Space by default, and in play it was Space that got the player off the title screen. This is worth stating explicitly because the plan originally listed only Enter, and a player who tries Enter alone on a screen where the game has not wired it may conclude the mod is broken.

It is also useful evidence: Space reaching Submit confirms the StandaloneInputModule is routing button events through the normal path, independently of the mod. Enter is additionally intercepted by the game's own InputValidate.CheckSubmit on the search field, which is why the two keys do not behave identically everywhere.

Key map and verbosity belong in a config file so they can be changed without a rebuild — screen-reader users often have strong, well-founded preferences here. Speech rate is left to the player's own screen reader, which already has their preferred settings. Note that MelonLoader's own preferences system is the component whose net35 build fails on this runtime, so this needs either the patched Tomlet or a config path of the mod's own.

Risks

Phase 02's size is still unknown

How much navigation this game actually uses decides whether Phase 02 is repair or construction, and only a running build can say. Mitigated by making that survey part of Phase 01, before any of Phase 02 is designed in detail — and by the fact that labelling, the larger half, is required either way.

Dynamic result thumbnails are the likeliest gap

Results are instantiated fresh on every query in PopulateDatabaseList(), and were only ever wired for mouse clicks. If they carry no navigation, they must be made focusable as they are built — on the exact code path the core loop runs through most often. Mitigated by patching that method directly, where the objects are created and their clip index is already in hand.

Compiled UnityScript is awkward to patch

Coroutines become generated state-machine classes with mangled names that are brittle to target directly. Mitigated by patching only stable public entry points — MyButtonPressed(), PopulateDatabaseList(), FillDetails() — and never the generated internals.

Speech and captions can collide

Caption output during playback will fight result announcements without an explicit priority policy. Mitigated by the interrupt-versus-append distinction, decided centrally in Narrator rather than ad hoc at each call site. The library's duplicate-suppression window helps but does not solve ordering.

Static analysis has already misled us twice

Two confident conclusions from reading files — "no keyboard handling" and "no input module in the scene" — were both wrong, because I searched one assembly and generalised, then used a string test that could not have found what it was looking for. Mitigated by treating the running game as the authority from Phase 01 onward, and by holding claims about engine behaviour provisional until observed.

Only real users can judge the result

Phrasing, verbosity, and pacing are the difference between usable and exhausting, and they cannot be validated by reading code. The build order front-loads the core loop so there is something worth testing early, and verbosity is configurable rather than fixed.

Scope

The mod ships as a single archive extracted over the game folder, with no game files altered. Windows only — UniversalSpeech.dll is a Windows library, and the game's video playback here is the Windows-specific AVPro path.

The one-step install survives the loader switch, for a reason that only becomes visible once the loader is patched: because this build modifies MelonLoader, it must distribute MelonLoader, so its installer is not used at all. Running the installer would place stock assemblies that then need overwriting with the patched ones — strictly worse than extracting the correct layout once. Bundling is the only sensible path, and bundling means extraction.

So the packaging argument that originally chose BepInEx holds here unchanged: one archive, extracted into the game folder, nothing to run first. That is still the most reliable install to describe in a readme and to follow with a screen reader.

Out of scope: translating the game, changing the search algorithm or the five-result cap, and re-encoding video. The mod makes the existing game reachable; it does not redesign it.

We build no controller support. Her Story's core mechanic is typing arbitrary words into a search box — you hear a name and type it. A gamepad reaches that only through an on-screen keyboard, character by character, which is worse without sight rather than better. A keyboard is required to play regardless, so controller input could only ever supplement the non-typing parts. No work is spent on it.

The controller remains useful as a queryable surface, though, which is why Phase 01 logs it. Unity's navigation axes already accept gamepad input, so whatever a connected pad can drive, it drives through the same path we are inspecting. That makes it evidence about the input module rather than a feature to implement — and if gamepad navigation happens to work as a side effect, it works for free.
